# Lab 0: Environment Setup Guide

This directory contains the helper files for setting up your local Iceberg development environment. The services themselves are defined in `docker-compose.yml` in the project root, with their configuration under `config/`.

For every endpoint, name and credential in one place, see the [Connection Reference](../common/connection-reference.md).

## 🚀 Quick Start (3 Steps)

### Step 1: Navigate to the project directory

If you have not cloned it yet:

```bash
git clone git@github.com:thescriptingcave/iceberg-examples.git
cd iceberg-examples
```

### Step 2: Start all services

```bash
./lab0-setup/startup.sh
```

This runs `docker compose up -d`, then polls each service until it is ready (up to 5 minutes; the very first start also builds two images, so it can take a while). There is no need to run `docker compose up -d` first; if you already did, the script simply waits for the services.

### Step 3: Verify everything is running

```bash
docker compose ps
```

You should see output like:

```
NAME                  SERVICE       STATUS                    PORTS
iceberg-jupyter       jupyter       Up 4 minutes (healthy)    0.0.0.0:4040->4040/tcp, 0.0.0.0:8888->8888/tcp
iceberg-objectstore   objectstore   Up 4 minutes              0.0.0.0:3900->3900/tcp
iceberg-polaris       polaris       Up 4 minutes (healthy)    0.0.0.0:8181->8181/tcp
iceberg-postgres      postgres      Up 4 minutes (healthy)    0.0.0.0:5432->5432/tcp
iceberg-trino         trino         Up 4 minutes (healthy)    0.0.0.0:8080->8080/tcp
```

Two more containers, `iceberg-objectstore-bootstrap` and `iceberg-polaris-bootstrap`, run once at startup and then exit. `docker compose ps -a` shows them; both should say `Exited (0)`.

## 🔗 Access Points

| Service | URL | Login |
|---------|-----|-------|
| **JupyterLab (Spark)** | http://localhost:8888 | token (see below) |
| **Spark UI** | http://localhost:4040 | - (only while a `SparkSession` is running) |
| **Trino web UI** | http://localhost:8080 | any user name, no password |
| **Polaris REST API** | http://localhost:8181/api/catalog | OAuth2 client credentials `root` / `root` |
| **Polaris management API** | http://localhost:8181/api/management/v1 | OAuth2 client credentials `root` / `root` |
| **Garage S3 API** | http://localhost:3900 | generated key (see below) |
| **PostgreSQL** | `localhost:5432` | `polaris` / `polaris` |

There is **no** web console for the object store and **no** Polaris admin UI.

Get the JupyterLab token:

```bash
docker logs iceberg-jupyter 2>&1 | grep 'token=' | tail -1
```

The object-store access key is generated by Garage the first time it starts, so it is not written anywhere in this repo. To see it:

```bash
docker exec iceberg-trino cat /creds/garage-credentials.env
```

## 🧪 Verifying Your Setup

### Verify the object store (Garage)

Garage has no web console. Check that the bootstrap container created the bucket and key successfully (it prints `exited 0`):

```bash
docker inspect -f '{{.State.Status}} {{.State.ExitCode}}' iceberg-objectstore-bootstrap
```

Then look at the bucket:

```bash
docker exec iceberg-objectstore /garage bucket info warehouse
```

You should see `Global alias: warehouse` and a key with `RWO` permissions. The object count is 0 until you create your first table.

### Verify Polaris

Every Polaris call needs an OAuth2 bearer token. Get one, then ask for the configuration of the `lakehouse` catalog:

```bash
TOKEN=$(curl -s -X POST http://localhost:8181/api/catalog/v1/oauth/tokens \
  -d grant_type=client_credentials -d client_id=root -d client_secret=root \
  -d scope=PRINCIPAL_ROLE:ALL | python3 -c "import json,sys; print(json.load(sys.stdin)['access_token'])")

curl -s -H "Authorization: Bearer $TOKEN" "http://localhost:8181/api/catalog/v1/config?warehouse=lakehouse"
```

You should see a JSON response containing `"prefix":"lakehouse"` and a list of supported endpoints. (Without a token Polaris answers `401`; without the `/api/catalog` prefix it answers `404`.)

### Verify Trino

```bash
docker exec -it iceberg-trino trino --catalog iceberg
```

You should see a `trino>` prompt. Try:

```sql
SHOW SCHEMAS;
```

### Verify Spark

Open JupyterLab at http://localhost:8888, create a notebook, and paste the `SparkSession` cell from the [Connection Reference](../common/connection-reference.md#spark-in-a-jupyter-notebook). Then run:

```python
spark.sql("SHOW NAMESPACES").show()
```

## 🗂️ Initialize the tutorial namespace

The labs keep their tables in the `tutorial` namespace (`lakehouse.tutorial.*` in Spark, `iceberg.tutorial.*` in Trino). `spark-init.sql` creates it, plus two small sample tables (`customers` and `orders`).

1. Copy the script into the `notebooks/` folder, which is mounted into the Jupyter container:

   ```bash
   cp lab0-setup/spark-init.sql notebooks/
   ```

2. In a notebook with the `SparkSession` from the [Connection Reference](../common/connection-reference.md#spark-in-a-jupyter-notebook), run:

   ```python
   from pathlib import Path

   sql_text = Path("spark-init.sql").read_text()

   statements = [s.strip() for s in sql_text.split(";") if s.strip()]

   for i, stmt in enumerate(statements, 1):
       print(f"\n--- Statement {i} ---")
       print(stmt)

       result = spark.sql(stmt)

       # Only display output for statements that return rows
       if stmt.lstrip().upper().startswith(("SELECT", "SHOW")):
           result.show(truncate=False)
   ```

   JupyterLab opens in `notebooks/`, so the relative path `spark-init.sql` is
   the copy you just made. If your kernel's working directory is somewhere
   else, use the absolute path instead:
   `Path("/home/jovyan/notebooks/spark-init.sql")`.

   The loop echoes each statement before running it, so a failure names the
   statement that caused it. Statements that do not return rows -- `CREATE
   NAMESPACE`, `USE`, `CREATE TABLE`, `INSERT OVERWRITE` -- run silently.

   Two consequences of splitting a commented file on `";"`:

   - The comment header rides along with the statement that follows it, and
     Spark accepts leading `--` lines, so this works. Never put a semicolon
     *inside* a comment, though -- the split would cut a statement in half.
   - A statement may begin with a comment line, so match on `lstrip()`ed text
     only when checking for `SELECT`/`SHOW`, as above.

The script is safe to run more than once: tables are created with `IF NOT EXISTS` and the sample rows are loaded with `INSERT OVERWRITE`. Check from Trino that both engines see the same tables:

```bash
docker exec iceberg-trino trino --execute "SELECT * FROM iceberg.tutorial.orders"
```

Both this script and Lab 1's seed step use `INSERT OVERWRITE`, so the two do not collide: whichever runs last replaces the rows rather than appending a second copy. You can run them in any order, repeatedly, and `customers` always holds three rows. That is why `INSERT OVERWRITE` and not `INSERT INTO` -- Iceberg has no primary keys, so a plain append would give you six rows with duplicate `customer_id`s.

## 🐛 Common Issues

### Issue 1: "Port 8080 is already in use" (or 8888, 8181, 3900, 5432)

**Solution:**

```bash
# Check what's using the port
lsof -i :8080

# Stop the conflicting service, then start again
./lab0-setup/startup.sh
```

For JupyterLab you can instead move the tutorial to another port: copy
`.env.example` to `.env`, set `JUPYTER_PORT=8889`, and rerun `startup.sh`.
`startup.sh` checks this port before starting, because a second JupyterLab on
port 8888 does not make Docker fail on macOS -- your browser just silently
reaches the wrong server.

### Issue 2: Services start but crash

**Solution:**

```bash
# Check logs
docker compose logs <service-name>

# Check that both bootstrap containers exited with code 0
docker compose ps -a

# Increase Docker memory (Settings → Resources → Memory → 8GB+)
```

### Issue 3: "Connection refused" when accessing services

**Solution:**

```bash
# Wait until every service answers (polls for up to 5 minutes)
./lab0-setup/startup.sh

# Check if services are running
docker compose ps
```

### Issue 4: "Namespace does not exist"

**Solution:** create the namespace first. In Spark:

```sql
CREATE NAMESPACE IF NOT EXISTS lakehouse.tutorial;
USE lakehouse.tutorial;
```

Or in Trino:

```sql
CREATE SCHEMA IF NOT EXISTS iceberg.tutorial;
USE iceberg.tutorial;
```

## 📊 Service Details

### Garage (Object Storage)

- **Port**: 3900 (S3 API)
- **Purpose**: Stores Iceberg data files and metadata in the `warehouse` bucket
- **Credentials**: generated at first boot, shared with the other containers via `/creds/garage-credentials.env`

### PostgreSQL (Database)

- **Port**: 5432
- **Purpose**: Database backend for the Polaris catalog
- **Credentials**: polaris/polaris

### Polaris (Catalog)

- **Port**: 8181 (Iceberg REST API under `/api/catalog`, management API under `/api/management/v1`)
- **Purpose**: Iceberg REST catalog - metadata broker
- **Configuration**: Connects to PostgreSQL; the `lakehouse` catalog is created by `config/polaris/bootstrap.sh`

### Spark (Compute Engine)

- **Port**: 8888 (JupyterLab), 4040 (Spark UI)
- **Purpose**: Primary engine for writes and transformations
- **Features**: Runs inside JupyterLab in local mode (no separate Spark cluster); the Iceberg jars are pre-installed

### Trino (Query Engine)

- **Port**: 8080 (server and web UI)
- **Purpose**: Interactive SQL queries
- **Features**: The `iceberg` catalog is rendered at startup from `config/trino/catalog/iceberg.properties.template`

## 📝 What's Happening Behind the Scenes

When you run `docker compose up`, the following happens:

```
┌──────────────────────────────────────────────────────────────┐
│                    Startup Sequence                           │
├──────────────────────────────────────────────────────────────┤
│                                                               │
│  1. Docker creates the network "iceberg-network"             │
│  2. Docker creates named volumes:                            │
│     - garage-meta, garage-data  (object store)                │
│     - postgres-data             (Polaris metadata)            │
│     - garage-creds              (generated S3 key)            │
│  3. Garage and PostgreSQL start                               │
│  4. objectstore-bootstrap creates the "warehouse" bucket      │
│     and an access key, writes it to garage-creds, exits       │
│  5. Polaris starts (PostgreSQL + the S3 key)                  │
│  6. polaris-bootstrap creates the root principal and the      │
│     "lakehouse" catalog, then exits                           │
│  7. Trino and JupyterLab start (connect to Polaris)          │
│                                                               │
└──────────────────────────────────────────────────────────────┘
```
